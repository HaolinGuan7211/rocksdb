**热点漂移的几类典型形态**，以及它们在 **key-range 尺度**上应该怎么“波动/移动”。这里的 key-range 尺度沿用 FAST’20 的思路：把 key-space 切成很多小 range（建议 range 大小接近平均每个 SST 的 KV 数），然后用“哪些 ranges 热、热多久、热得多强、热 keys 在 range 内如何分布”来定义漂移。

---

## 0) 先把参数语言统一（你设计负载时就围绕这四个量）

假设你把 key-space 切成 `R` 个 ranges（range_id = 0..R-1），那漂移负载可以用四个时间序列来描述：

1. **热范围集合**：`H(t) ⊂ {0..R-1}`（哪些 ranges 在 t 时刻是热的）
2. **热范围权重**：`w_r(t)`（每个热 range 在 t 时刻承担多少请求）
3. **range 内热 key 分布**：`p(key | range, t)`（热 key 是否聚在 range 的某个子区间；是否偏向 range 尾部等）
4. **漂移速度/时间尺度**：阶段长度/滑动步长（多快换一次热点）

你要的“key-ranges 尺度波动”主要体现在 1) 和 4) ：**热点覆盖多少个 ranges、这些 ranges 在 range_id 空间上怎么移动**。

---

## 1) Step 漂移（突变跳转）：热集合在少数 ranges 之间“整块跳”

**形态**：每隔 `T`（比如 5–30 分钟），热点从一组 ranges 突然切换到另一组几乎不重叠的 ranges。

* key-range 尺度怎么波动：

  * `|H(t)|` 维持很小（例如占总 ranges 的 1%–5%），但 `H(t)` 的**位置**突然跳
  * 例如：`H = {10..13}` → `{120..123}` → `{40..43}`（“小窗口大跳”）

* 适合模拟：

  * 推荐/广告里“热点人群/热点内容”突然切换
  * 节点故障/流量重路由导致的 key-range 热点迁移

* 你关心的效应：

  * cache 命中会出现“骤降—再爬升”的周期（典型漂移信号）
  * 特别能测“重新暖机时间（re-warm time）”与尾延迟尖峰

---

## 2) Rolling 漂移（滑动窗口）：热点在 range_id 上“平滑滑动”

**形态**：热点覆盖一个连续窗口，窗口中心随时间缓慢移动。

* key-range 尺度怎么波动：

  * `|H(t)|` 固定（比如 8 个 ranges），但窗口**每个时间步滑动 1 个 range**
  * 例如：`H = {10..17}` → `{11..18}` → `{12..19}` …
  * 也可以“加速度”：有时滑 1、有时滑 3（模拟热点移动速度变化）

* range 内热 key 分布（可选增强真实感）：

  * 让热 key 偏向 range 尾部（模拟“新 ID 更热”那类现象）
  * 那么随着窗口滑动，热点也像“不断追着最新产生的数据走”

* 适合模拟：

  * 时间序列特征、日志/消息类业务按时间递增 key
  * “最新内容更热”的 feed/图更新

* 你关心的效应：

  * cache 命中不会完全崩溃，而是呈“带宽式损耗”：旧热范围逐渐冷却，新热范围逐渐升温
  * 更考验预取、以及“不要把刚冷掉的一整段误保留太久”的替换策略

---

## 3) Cyclic 漂移（周期轮换）：多个热点簇之间循环切换

**形态**：热点在几个固定簇之间来回轮转：A→B→C→A…

* key-range 尺度怎么波动：

  * 每个簇本身很小（例如每簇 4–16 个 ranges），簇之间相距很远
  * `H(t)` 在簇之间跳，但会**回到旧簇**（与 step 漂移不同）

* 适合模拟：

  * 日夜周期、定时任务触发的业务热点
  * “反复出现”的热内容集合

* 你关心的效应：

  * 这类负载最适合评估“是否值得保留一部分历史热点”
  * 如果你的 cache 策略能记住上一次的热点簇，回到 A 时命中率应更快恢复

---

## 4) Burst 漂移（突发热点叠加）：在稳定热点上叠加短暂爆发热点

**形态**：存在一个长期稳定的热集合 `H_base`，同时随机出现短促的 `H_burst`。

* key-range 尺度怎么波动：

  * `H_base` 固定（例如 2–4 个 ranges，长期占 60% 请求）
  * `H_burst` 突然出现（例如 1–2 个 ranges，占 20%–40% 请求，持续 10–60 秒），位置随机或按事件触发

* 适合模拟：

  * 热点事件、热点内容爆发
  * 批处理/定时作业短时间打到某段 key-range

* 你关心的效应：

  * 是否发生**cache pollution**（burst 把 base 热块挤掉，burst 结束后命中率反而更差）
  * 对短 scan 很关键：因为你还有“200 台阶”这种中等 scan，会放大污染风险

---

## 5) Diffusion 漂移（热点扩散/收缩）：热点集合大小本身随时间变化

**形态**：热点从很窄的范围逐渐扩散成更宽，再收缩回去（或反过来）。

* key-range 尺度怎么波动：

  * `|H(t)|` 不固定：例如从 2 个 ranges 扩到 32 个，再回到 2 个
  * 位置可固定或缓慢移动

* 适合模拟：

  * 推荐候选集扩大/收敛、召回策略切换导致访问范围变化
  * 分片重均衡导致热范围变“散”

* 你关心的效应：

  * 当 `|H(t)|` 变大时，热点 blocks 工作集会突然超过 cache，命中率会出现“相变”式下跌
  * 这类负载能非常清晰地展示“cache 容量 vs 热工作集”的拐点

---

## 6) 你如何把这些“漂移形态”映射到论文的 key-range 局部性观点？

FAST’20 的关键点是：真实负载热 KV **集中在少数 key-ranges**，局部性越强，cache hit 与 I/O 越好；并且建模时强调在 range 内让热 KV **彼此靠近**。
所以你做漂移时，只要满足两条，就“符合论文语义”：

1. 任意时刻 `t`，热请求主要落在一个很小的 `H(t)` 上（局部性强）
2. 随时间 `t`，`H(t)` 在 range_id 空间上按某种规律移动/跳转（漂移）

---

## 7) 一个最简“漂移负载”模板（你可按它自由扩展）

* 切分：R=32 或 64 个 ranges（range 粒度按 SST KV 数）
* 任意时刻：Top K ranges 承担 90% 请求（K/R ≈ 1%–5%）
* 每个阶段：持续 T=5 分钟
* 漂移方式：从上面 5 类里选一种
* range 内：热 key 聚集在一个连续子区间（可选“偏尾部”增强真实感） 
* scan：保持短 scan 主导，并固定比例注入 scan_len=200 台阶
